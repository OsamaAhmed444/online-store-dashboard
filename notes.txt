Date: 2026-09-06 (session 8) — Fixed Users page to match the real API schema (from the live Swagger docs)

You shared the actual API docs (https://e-commerce-api-3wara.vercel.app/api-docs). Rather than going only off the screenshots, fetched the real OpenAPI spec from `/api-docs/swagger.json` to get the exact request schemas, and found the Add/Edit User forms were sending fields the API silently ignores or rejects:
- `POST /users/add` only accepts `username`, `email`, `password` (required) and `phone` (optional) — no `firstName`/`lastName`/`role`. The Add User form was sending firstName/lastName/role, which the API has no field for at all (the User schema itself only has username/email/phone/avatar/role/addresses/isVerified — there's no name-splitting concept in this API).
- `PATCH /users/{id}` only accepts `username`, `phone`, `avatar` — no `email`/`password`/`role`. The Edit User form was sending email/password/role, none of which that endpoint can change.
- Role changes have their own dedicated endpoint: `PATCH /auth/change-role` with body `{ userId, role }` (role is `"admin"` or `"customer"`) — this was never called anywhere in the app.
- Confirmed, per the spec, there truly is no user-verification endpoint anywhere (only OTP verification during registration/password-reset, not an admin "verify a user" action) — the existing "Verify" button in the Users table only ever showed `toast.error('The API does not provide a user verification endpoint.')` and could never succeed.

What was fixed:
- `src/api/auth.js`: added `changeRole(userId, role)` calling the real `PATCH /auth/change-role`.
- `src/pages/UsersListPage.jsx`:
  - Add User form now only collects/sends `username`, `email`, `password`, `phone` (matching `POST /users/add`).
  - Edit User form now only collects/sends `username`, `phone`, `avatar` (matching `PATCH /users/{id}`) — email/password/role are no longer offered there since the API can't act on them via that endpoint.
  - Replaced the dead-end "Verify" button with a real "Promote to admin / Demote to customer" action that calls the new `changeRole` API, behind the same confirm-dialog pattern already used for delete.
  - `normalizeUser` simplified to stop guessing at `firstName`/`lastName`/`fullName` fields that don't exist in the real User schema, and reads `isVerified` directly (matching the schema) instead of guessing at alternate field names.

Verification:
- `npm run build` completes successfully.
- Same limitation as prior sessions — no admin credentials to click through the live authenticated Users page, so please verify Add/Edit/Promote-Demote/Delete users against the real API in your own session.
